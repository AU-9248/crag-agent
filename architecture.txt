PROJECT ARCHITECTURE: Local Corrective Retrieval-Augmented Generation (CRAG) Chatbot

This document provides a deep dive into the technical architecture of the local CRAG chatbot. The application is logically divided into three layers: the Client (Frontend), the API Server (Backend), and the Agentic Workflow (LangGraph & Local LLMs).

---------------------------------------------------------
1. THE CLIENT TIER (Frontend UI)
---------------------------------------------------------
File: `static/index.html`
Technology: Vanilla JavaScript, HTML5, Tailwind CSS (via CDN)

- Layout & Styling: A modern, responsive, ChatGPT-like interface utilizing Flexbox and absolute positioning for strict, overflow-safe layout constraints.
- Real-Time Streaming: Instead of waiting for the entire LLM chain to finish, the UI connects to the backend via Server-Sent Events (SSE). It parses a stream of JSON events (`init`, `update`, `done`, `error`) to dynamically render a live "Execution Trace" (the thinking process) and stream the final answer.
- Local Storage State: JavaScript variables track the active `conversationId` to seamlessly route follow-up questions to the correct chat history thread.

---------------------------------------------------------
2. THE SERVER TIER (Backend API & Database)
---------------------------------------------------------
Files: `server.py`, `database.py`
Technology: FastAPI, SQLite, SQLAlchemy, SSE-Starlette

Database Architecture (`database.py`):
- Uses SQLAlchemy ORM to manage a local `chat_history.db` SQLite file.
- Contains two tables with a One-to-Many relationship:
  1. `Conversation`: Stores chat thread metadata (ID, Title, Created At).
  2. `Message`: Stores the actual conversation (Role, Content) as well as structured JSON strings for the AI's "sources" and internal "trace" steps.

API Server (`server.py`):
- Exposes standard REST endpoints (`/api/conversations`) for the frontend sidebar to load and delete historical chats.
- Exposes an asynchronous `/chat` endpoint that acts as the bridge between the user and the LangGraph agent. It reads the full chat history from SQLite, injects it into the agent's state, executes the `astream` graph traversal, and yields SSE events as the graph progresses from node to node.

---------------------------------------------------------
3. THE AGENTIC WORKFLOW (LangGraph & Local Models)
---------------------------------------------------------
File: `graph.py`
Technology: LangGraph, LangChain, Ollama (Llama 3.1 & Nomic Embeddings), FAISS, Tavily API

Knowledge Base Initialization:
On startup, the system scans the root directory for `.pdf` files, chunks them using a `RecursiveCharacterTextSplitter`, and embeds them into a local FAISS vector store using `nomic-embed-text`. If the index already exists on disk, it simply loads it to dramatically speed up server boot times.

The Graph Topology (State Machine):
The agent operates on a shared `State` object (a TypedDict storing the question, docs, verdict, web results, etc.) and routes through the following nodes:

1. Retrieve (`retrieve_node`)
   Extracts the user's question and performs a semantic similarity search against the local FAISS PDF index.

2. Evaluate (`eval_each_doc_node`)
   Uses `llama3.1:8b` configured with Structured Output (JSON) as a strict judge. It scores each retrieved chunk from 0.0 to 1.0. 
   - If any score > 0.7: Verdict is "CORRECT".
   - If all scores < 0.3: Verdict is "INCORRECT".
   - Else: Verdict is "AMBIGUOUS".

3. Routing Decision (`route_after_eval`)
   If the verdict is CORRECT, the graph bypasses web search and goes straight to the Refine node. If INCORRECT or AMBIGUOUS, it triggers the web fallback.

4. Rewrite Query (`rewrite_query_node`)
   If fallback is triggered, an LLM prompt rewrites the user's question (taking past chat history into context) into an optimized, keyword-dense string suitable for a search engine.

5. Web Search (`web_search_node`)
   Calls the Tavily API with `include_raw_content=True`. This scrapes the full HTML text of the top 5 search results.

6. Semantic Filter (`refine`)
   Because raw web data is massive and easily exceeds an LLM's context window (and slows down generation), this node chunks the raw text and dynamically creates an *ephemeral (temporary)* FAISS index in memory. It immediately searches this temporary index to pull only the top 10 most relevant chunks. This replaces slow, sequential LLM filtering with lightning-fast semantic math.

7. Generate (`generate`)
   The final LLM call. It injects the refined context and the conversational chat history into the prompt, forcing the LLM to synthesize an answer based *only* on the provided context.

---------------------------------------------------------
SUMMARY OF DATA FLOW
---------------------------------------------------------
User Question -> UI -> FastAPI -> Retrieve Local PDF -> Evaluate -> (Optional Web Search -> Fast Semantic Filter) -> Generate Response -> Streaming Output (SSE) -> SQLite Storage -> UI Render
